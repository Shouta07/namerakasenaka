# 監査 2026-08 — SaaS として販売できるか

**方法**: 本番ビルド（`next build` → `next start`）で 49 ルートを 390 / 820 / 1280px で巡回、
依存の脆弱性・秘密情報・テナント分離・テスト・実装状況を実測。
**結論**: **画面は売れる。事業としてはまだ売れない。** 詰まっているのは UI ではなく、
契約に必要な土台。うち B2（同意の強制）と B3（検査の取り込み）は 2026-08 に実装した。

## 2. 売る前に必ず塞ぐもの（ブロッカー）

### B1. 認証とテナント分離が「デモモード」で無効化されている
`middleware.ts` は環境変数が未設定だと**全ルートを素通し**にする。
デモとしては正しいが、本番テナントを迎える前に、
デモモードと本番モードの切り分け（環境ごとの明示フラグ）が要る。

### ~~B2. 同意なし LINE 送信のサーバ強制が未実装~~ → 検査表示ぶんは実装済み
同意は**フラグではなく記録**（いつ・誰が・何について・どう確認したか）にした。
判定は `lib/labtest/consent.ts` の純関数に集約し、`POST /api/labtest/publish` が
同意なし・取り消し済みの公開要求を **403** で止める。実測で確認済み:
UI を迂回して API を直接叩いても 403、同意を取り消した瞬間から患者側の表示も消える。

**残り**: LINE 送信（`line_share`）の強制は、B4 の配信実装と同時に入れる。
同意の目的は分けてあるので、判定関数はそのまま使える。

### ~~B3. 検査結果の取り込み — 本番では保存されない~~ → 保存経路をつないだ

前回この項目を「実装済み」と書いたのは**言い過ぎだった**ので訂正する。

できていること: 取り込みの導線（ドラッグ&ドロップ / CSV / TSV / コピペ）、
人が確認する段、同意ゲート、患者側の可視化。パーサと同意判定は純関数で 38 テスト。

**塞いだこと**: `POST /api/labtest/imports` と `POST /api/consents` を追加し、
保存の入口を `lib/labtest/repository.ts` に集約した。画面は必ず API を通る。

そして**マイグレーションを本物の PostgreSQL に流した**（初めて）。
その結果、書いただけでは気づけない不具合が2つ出た:

1. **0008 が落ちていた** — 既定タグの seed に UUID として不正な組織IDを直書き。
   本番なら初回デプロイで確実に失敗する状態だった
2. **患者が自分の検査を永久に見られなかった** — ポリシー式の中の
   `exists (select ... from consents ...)` に**内側もRLSがかかる**ため、
   患者からは常に0行になっていた。security definer の関数に切り出して解決

**残り**: PDF の直接読み取り（いまは「表を選択してコピー」と案内して逃がしている）。
本番 Supabase への実接続はまだ（スキーマとポリシーは検証済み）。

### B4. LINE 配信が未実装（接続の土台は実装済み）
送信そのものはまだ。「LINE で届く」を売り文句にしている以上、契約前に必須。

**実装済み**: 店舗が自分の公式アカウントを接続する導線
（`/admin/settings/line`）、テナントごとの署名検証つき webhook、
`(organization_id, line_user_id)` での患者ひもづけ（マイグレーション 0011）。
鍵は店舗が自分で登録し、API もログも監査ログも鍵を出さない。

**残り**: メッセージの送信、週次テンプレ、返信の解析、疎通確認の実接続。
送信時に `canSendLine()` を通すこと。

**前提が確定した**: 公式アカウントは**店舗が自分で持っている**。
自社で束ねるのではなく、店舗のアカウントに接続する（BYO-LINE）。
通信費は店舗負担になるが、そのかわり **店舗のチャネルの鍵を預かる**リスクと、
**患者IDが店舗ごとに別物になる**というスキーマ上の制約が乗る。
着手前に `docs/field-cx/security-and-cost.md` の3章を読むこと —
鍵を預からずに済む方法（モジュール）があれば、設計そのものが変わる。

## 4. 磨き残し（売れるが、直したい）

### 済（2026-08 の磨き込みで塞いだ）

- **タップ領域 44px 未満: 0 件**。390 / 820 / 1280px の3幅 × 49ルートで実測。
  密なUIは見た目を保ったまま当たり判定だけ広げる `.tap-44`（globals.css）と
  `Button size="sm"` の擬似要素で解決した。iPad のサイドバーも 44px に。
  文中に埋まったリンクは WCAG 2.5.8 の inline 例外として対象外
- **横スクロール 0 ページ**（820px のスタッフ画面で3件出ていたものを解消）。
  原因は flex 子の `min-width:auto`。レイアウトの列に `min-w-0` を入れた
- **顧客画面の入力欄 0 件** — 到達不能なまま残っていた `/c/self-log` を削除。
  「顧客は記録しない、やりとりは LINE」の原則とコードを一致させた
- **再発防止**: `src/lib/compliance/__tests__/source-hygiene.test.ts` が
  実在名の再混入・`.tap-44` の消失・顧客画面への入力欄復活を検知する

### 残

- **依存の脆弱性 — 本番依存で high 3件**（`next` 本体・`postcss`・`sharp`）。
  `npm audit fix` を実行して next を 15.1.0 → 15.5.22 に上げ、
  `form-data` など2件は解消した。**残る3件は Next 16（メジャー）が要る** —
  実測で `isSemVerMajor: true`。
  `sharp` は libvips の CVE なので、**患者の写真を扱う前に上げること**。
  テスト用の `vite` / `vitest` にも major が要る（critical 1件を含む）
- TODO/FIXME が 9 箇所。うち 8 件は `TODO(phase-1)` で、
  B1/B3 の本番接続点を指している（消すのではなく、塞いだら消える印）
- 実在名の扱い: **すべて非掲載**（医療機関名・医師名・店舗名・担当者名）。
  画面・識別子・URLスラッグまで除去済み
