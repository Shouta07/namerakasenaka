# 価値検証の最小構成

**検証したい仮説はひとつ。**

> 血液検査を分かりやすく見せて伴走すると、患者が続き、店舗はそれにお金を払う。

この仮説の真偽を変えない機能は、どれだけ作り込んであっても外す。

---

## なぜ削るのか

機能が多いほど、

1. 店舗に説明する時間が増える（導入が重くなる）
2. 使われない画面の不具合に人手を取られる（原価が増える）
3. **「何が効いたのか」が分からなくなる**

**3つめが致命的。** 同時に10個出すと、続いた理由も、
続かなかった理由も、永久に分かりません。

## 残したもの

| 誰が | 何をする |
|---|---|
| 施術者 | 検査票をドラッグ&ドロップ → 読み取り結果を確認 → 同意を確かめて公開 |
| 患者 | 自分の検査結果を、意味と一緒に見る |

画面はこれだけ:

```
店舗   /admin/customers  … 検査と伴走（取り込み・同意・公開）
       /admin/clients    … 顧客
       /admin/invites/new… 招待
       /admin/settings/line … 公式LINEの連携

患者   /c/progress       … 今日
       /c/guide          … 血液診断
```

患者のタブは**2つ**。増やすと、続いた理由がどれだったのか分からなくなります。

## 外したもの

**コードは消していません。** 消すと戻せず、検証済みのテストも失われる。
ナビから外し、既定をオフにしただけです。仮説が通ったら戻します。

| 外したもの | なぜ | いつ戻すか |
|---|---|---|
| LINEの自動送信 | 店舗は公式LINEの管理画面から手でリンクを送れる。自動化しなくても「見て続くか」は測れる | 週次の手送りが回り、手間がボトルネックになったとき |
| LINEの返信解析 | 送信すら検証していない段階で、返信の構造化は早い | 自動送信を入れて、返信が来るようになってから |
| 接客コパイロット | 提案が効いたのか可視化が効いたのか、切り分けられなくなる | 可視化で継続率が動くと確認できたあと |
| 接客ロールプレイ | 別の商品。育成の課題は継続伴走とは独立 | 伴走が売れて、育成の相談が出てきたとき |
| 成約ダッシュボード | 見るデータがまだ無い。1店舗ぶんは表で足りる | 3店舗以上、または半年ぶん溜まったとき |
| 症例ライブラリ | 別の接客支援。同時に出すと何が効いたか分からない | 検証が終わり、次のテーマを選ぶとき |
| 離脱予兆 | 離脱を検知するには、まず継続するデータが要る。順番が逆 | 記録が数か月ぶん溜まったとき |
| エビデンス集計 | 集計する母数がまだ無い | 患者20人・3か月ぶん溜まったとき |
| 学習コンテンツ | 仮説の真偽を変えない。別商品に切り出す判断済み | 別商品として値付けするとき |
| アプリ内課金 | 1〜3店舗なら請求書で足りる | 5店舗を超えて請求作業が負担になったとき |

一覧は `src/lib/vitality-design/mvp.ts` が単一の情報源。
テストが「理由と戻す条件が書かれていること」を強制します
（`why` が「後で」だけ、`bringBackWhen` が「同上」だけ、は落ちる）。

## 何をもって成功とするか

**先に決めておく。** あとから決めると、都合よく解釈できてしまいます。

| 指標 | 目標 | なぜ |
|---|---|---|
| 患者が自分の検査ページを見る | 公開した患者の **6割以上**が7日以内に1回以上開く | 見られなければ、価値以前の問題 |
| 見た患者が、もう一度開く | 初回閲覧者の **3割以上**が2回目を開く | 1回で終わりなら説明資料であって伴走ではない |
| 店舗が2人目以降も取り込む | 導入4週間で **5人以上** | 現場の評価は言葉ではなく回数に出る |
| 店舗が有償化に合意する | **8週間**の無償期間の終わりに1店舗が合意 | 最終的にこれだけが本当の検証 |

上3つは、最後のひとつに至る途中経過にすぎません。

## 削っていないもの（削れないもの）

- **同意の記録と強制** — 要配慮個人情報を扱う以上、法令の要求。機能ではなく前提
- **テナント分離（RLS）** — 1回漏らしたら事業が終わる。検証段階でも省けない
- **監査ログ** — 誰が何をしたか説明できない状態で、患者データは預かれない

## 検証に入る前に残っている作業

1. **本番 Supabase への実接続**（1日）— スキーマとポリシーは実DBで検証済み
2. **Next 16 への更新** — `sharp` の libvips CVE。**患者の写真を扱う前に**
3. サイバー保険と、店舗との責任分界の契約書（`security-and-cost.md` 5章）

## 付録: システム名を変える手順

名前は5つの形でコードに散らばります。表示名だけ直しても、
識別子・ファイル名・URLスラッグに旧称が残り、あとから見つけにくくなります
（`import` パスの中など）。

```bash
# 1. 下見（何が変わるかだけ見る。書き換えない）
python3 scripts/rename-product.py "Vitality Design" "新しい名前" --check

# 2. 実行
python3 scripts/rename-product.py "Vitality Design" "新しい名前"

# 3. 検証（この順番で。.next を先に消す）
rm -rf .next
npx tsc --noEmit && npx eslint src && npx vitest run
./scripts/verify-migrations.sh
npx next build
grep -ri "vitality-design" src docs supabase   # 0件になること
```

置き換わるもの:

| 形 | 例 |
|---|---|
| 表示名 | `Vitality Design` → 画面・ドキュメント |
| PascalCase | `VitalityDesignModuleId` → 型・コンポーネント |
| SCREAMING_SNAKE | `VITALITY_DESIGN_MODULES` → 定数 |
| kebab | `/vitality-design/*`・`--vitality-design-nav-h`・`vitality-design-demo-v1` |
| ディレクトリ | `src/app/vitality-design`・`docs/vitality-design`（`git mv` で履歴を残す） |

### 手でやるとハマるところ（スクリプトが吸収済み）

- **置換の順番** — 短い kebab を先に当てると `VitalityDesignModuleId` が壊れる
- **日本語に接する表示名** — 「Vitality Designは」「Vitality Design内」は `\b` が立たない。
  単語境界に頼ると取りこぼす
- **ハイフン入りのオブジェクトキー** — `vitality-design:` は引用符が無いと構文エラー。
  実行後に検出して報告する
- **`.next` の古い生成型** — 消さずに `tsc` を回すと旧パスを参照して落ちる。
  改名が失敗したように見えるが、原因はキャッシュ

### やり直したくなったら

`git mv` はステージに残るので、**`git checkout .` だけでは戻りません**
（内容は戻るがディレクトリ名は新しいまま、という不整合になります）。
確実に戻すには、コミット前なら:

```bash
git reset --hard HEAD && git clean -fd
```

### 注意

- **localStorage の名前空間が変わります。** デモで入力したデータは引き継がれません
- `package.json` の `"name"` は触りません（画面にも URL にも出ないビルド識別子）。
  変えるならリポジトリ名ごと揃えるほうが自然です
- 本番の Vercel ドメインは別途変更が必要です（コードの外）

## 資料請求 → お試しの導線

想定している流れ:

```
資料請求が届く → 資料と一緒に /trial のリンクを送る
  → 相手が開く → 登録なしでその場で触れる → 導入の相談へ
```

設計の軸は **相手に何も要求しない**こと。

- **アカウント登録なし** — メールもパスワードも不要
- **設定なし** — LINE の接続も Supabase も要らない
- **データがその端末から出ない** — ここが最重要

### なぜ「端末から出ない」が最重要か

試用のお客様は、**実際の患者さんの検査票を持っています。**
それを落として試したくなるのが自然で、そのとき
「契約前の会社に患者データを渡してよいのか」で必ず手が止まります。

答えは「渡していません」。検査値はブラウザの中だけに保存され、
当社のサーバーには送信されません。

**口約束にしないため、実装でも守っています。**
以前は、デモでも取り込みの API に検査値を送っていました
（保存はしないが、リクエストとして通り、ログに残る可能性があった）。
お試しでは API を通さず、ブラウザ内で完結させるよう直しています。

Playwright で実測: 検査票を取り込んでも、**検査値を含む POST は0件**。

> 例外は公開の API。あちらには同意ゲートがあり、通さないと
> 「同意が無いと公開できない」ことを確かめられなくなります。
> ただし検査値そのものは運びません。

### お試し中の見え方

全画面の上部に「お試し中 / N日目 / **入力したデータはこの端末から出ません**」を出します。
バナーは普通なら邪魔ですが、ここでは出す理由があります:

- 「端末から出ません」は**入力する瞬間に見えていないと意味がない**
- お試しだと忘れたまま本番運用に入られると事故になる

商談で画面を見せるときは邪魔なので、プレゼンモードでは隠れます。

### 3分で山場まで運ぶ

「自由に触ってください」では、価値のある画面にたどり着かないまま終わります。

1. 検査結果を取り込む（読み取れた項目と、読み取れなかった行が並ぶ）
2. 同意を確認して公開する（同意が無いと公開できない）
3. **患者さんの画面を見る**（数値が図になり、意味と次の一歩が並ぶ）

3が山場です。ここまで着かなければ、お試しは失敗しています。
