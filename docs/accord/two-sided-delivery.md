# Accord × hisrecoveries — 二面配信設計（院側入力 → 個々人へ出し分け）

**版**: v1.0（2026-07）
**着想（ユーザー）**: サロン/クリニックが入れたデータやコメントが、Accordを通じて
**「その人に必要なものだけ」個々の患者に表示される**設計にしたい（hisrecoveries = 患者側の面）。

> ⚠️ hisrecoveries.com/member は認証必須で実画面を確認できていない。本設計は
> ユーザーの意図 + 本リポジトリの既存資産（/share・/c/guide・recovery-guide・lessons）から起こす。
> 実画面の表示要素が判明したら §7 の対応表を更新すること。

---

## 1. 二面モデル（1つの背骨に、2つの顔）

```
   院側（B2B・Accord）                     背骨（共有）              患者側（B2B2C・hisrecoveries）
 ┌──────────────────────┐          ┌────────────────────┐        ┌──────────────────────┐
 │ スタッフが入力する     │          │ 共有Identity        │        │ 患者が見る            │
 │ ・カウンセリング記録   │──入力──▶ │ 共有DB(customers等) │──表示─▶│ ・自分の経過(写真/数値)│
 │ ・施術記録・経過写真   │          │ + 可視性/宛先/配信  │        │ ・院からのコメント     │
 │ ・患者へのコメント     │          │   ルール層          │        │ ・今日のひとつ         │
 │ ・レッスン/ガイド割当  │          │ + 同意ゲート        │        │ ・自分向けレッスン     │
 │ copilotが「送る」提案  │          └────────────────────┘        │ ・次回予約/回復ガイド │
 └──────────────────────┘                                        └──────────────────────┘
        ▲ 患者の自己記録・反応（今日のひとつ実行、既読、フォロー返信）は逆向きに院側へ戻る
```

**要点**: hisrecoveries は「別システム」ではなく、**共有背骨の患者ビュー**。院側が入れたもののうち
「患者に共有」とマークされ、その人の段階・悩みに合うものだけがレンダリングされる。既に
`/share/[token]`（LINE配信の個人ページ）がこの原型。hisrecoveries はそのログイン版・常設版。

## 2. 設計の核 = 「可視性 × 宛先 × 配信タイミング」の3属性

「全部出す」でも「院が手で毎回選ぶ」でもない。**院側の各データに3属性を持たせ、患者側は
その射影を見る**。これが "必要なものだけ" を機械的に実現する肝。

| 属性 | 値 | 意味 |
|---|---|---|
| **audience（宛先）** | customer_id | 誰に向けたものか（DM的な指定コメント）／null=段階ルールで自動配信 |
| **visibility（可視性）** | `internal` / `shared` | 院内メモか、患者に見せるか。既定は internal（誤配信を防ぐ） |
| **surface_when（配信条件）** | 段階(初回/術後1週/1ヶ月…) / 悩み(背中/顔) / トリガー(写真更新時 等) | いつ・どの人に出すか |

患者ページの表示 = `SELECT ... WHERE audience=me AND visibility='shared' AND surface_when が今の私に合致 AND 同意あり`。

## 3. 「院→患者」への配信は3経路（すべて既存資産に対応）

| 経路 | 中身 | 既存資産 | 追加するもの |
|---|---|---|---|
| **① 指定コメント** | スタッフが特定患者へ書くひとこと（「経過順調です。次回は保湿を」） | timeline_events | `visibility='shared'` トグルを付ける |
| **② 自動パーソナルガイド** | 検査/悩みからAIが個別生成する回復ガイド・図解 | recovery-guide（RecoveryGuideJson）/ 翻訳辞書 | 段階での出し分け（surface_when） |
| **③ 段階・悩み別コンテンツ** | その人の段階と悩みに合うレッスン/今日のひとつだけ | lessons + progress / follow-loop | 悩みタグ×段階のマッピング |

**copilot の役割**: 「〇〇様は術後1週。保湿コメントの好機です → [コメントを送る]」のように、
**院側スタッフに"何を誰に共有すべきか"を提案**する（配信の自動化ではなく、人の承認を挟む）。

## 4. 双方向 — 患者の反応が院に戻る

一方通行にしない。患者側の行動が院側の材料になり、堀(#1)に貯まる:
- 今日のひとつの実行・既読・フォロー返信・自己ログ → 院側タイムライン & at-risk & copilot へ
- 「見せた情報にどう反応したか」が、②③のパーソナライズ精度を上げる学習データになる

## 5. 同意ゲート（二面だからこそ厳格に）

- 院→患者: `line_consents` / アカウント同意のスコープ内のものだけ `shared` にできる（サーバ強制）
- 患者→院: 患者が「院と共有する」を選んだ自己記録だけが院側に見える（患者のプライバシー主権）
- 患者の削除要請 → 共有DBを横断カスケード（Accord側エビデンス + hisrecoveries側）。**削除カスケードは初日に設計**（要配慮情報）

## 6. データモデル（既存への最小追加）

```sql
-- 既存 timeline_events に付与
ALTER: timeline_events
  + audience_customer_id  -- 指定配信（null=段階ルール）
  + visibility            -- 'internal' | 'shared'（既定 internal）
  + surface_rule jsonb    -- {stage?, concern?, trigger?}
  + shared_at, shared_by

-- 配信済みの記録（患者が何を受け取ったか＝既読/反応の土台）
deliveries(id, customer_id, source_kind, source_id, delivered_at,
           read_at, reaction jsonb)

-- 患者アカウント（hisrecoveries ログイン。共有Identityの患者側）
patient_accounts(id, customer_id, auth_user_id, consent_scope jsonb, created_at)
```

顧客レコード `customers` が院側(Accord)と患者側(hisrecoveries)の**結合点**。1人の患者 =
院から見た customer = hisrecoveries のログインユーザー、が同一 id で繋がる。

## 7. hisrecoveries 表示要素の対応（※実画面確認後に更新）

| 患者が見る想定要素 | 供給元（院側/自動） | 出し分けキー |
|---|---|---|
| 経過写真 before/after | photos（院側 + 患者自撮り） | 本人分のみ・同意 |
| 数値の推移（肌状態・自己評価） | evidence / self-log | 本人・段階 |
| 院からのコメント | timeline(shared・指定) | audience=本人 |
| 今日のひとつ | follow-loop | 段階・悩み |
| 自分向けレッスン | lessons | 悩みタグ×段階 |
| 回復ガイド | recovery-guide(AI) | 本人の検査/悩み |
| 次回予約・リマインド | （data-import 予約 or 手入力） | 本人 |

## 8. 正直な設計上の勘所（ここを外すと事故る）

1. **難所は"表示"ではなく"必要なものだけ"のフィルタ**。出しすぎ＝ノイズで患者が離れる／
   出さなすぎ＝放置された感。→ **段階ルール(自動) + スタッフの共有トグル(手動) + copilotの提案(AI)** の
   三点で決め、患者側に「なぜこれが出ているか」の一言（例: 術後1週の方へ）を添えて透明にする。
2. **既定は internal**。共有は明示アクション。医療情報の誤配信は一発で信頼を失う。
3. **hisrecoveries を院側ロジックから独立した"読み取り面"に保つ**（スキーマ分離 `recoveries`）。
   院側の複雑な権限・KPIを患者面に持ち込まない（前回の"神アプリにしない"に整合）。
4. **これは堀そのもの**: 院のコメント×患者の反応×経過が1本の背骨に貯まる（moat #1/#2）。
   二面を最初から共有Identity/DBで繋ぐ判断は、この蓄積のために正しい。
