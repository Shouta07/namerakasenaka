# 汎用SaaSとして売るときの、コストとセキュリティ

**前提となる一文**: この商品が持つのは血液検査の結果 —
個人情報保護法の**要配慮個人情報**です。
「SaaS」ではなく「**複数テナントの要配慮個人情報を預かるSaaS**」として設計する。
コストも守り方も、ほぼすべてこの一文から出てきます。

要配慮個人情報だと何が変わるか:

- 取得に**本人の同意が必須**（オプトアウトによる第三者提供は使えない）
- 漏えいは **1件でも**個人情報保護委員会への報告義務 + 本人への通知義務
- 提携クリニックと組むなら、**3省2ガイドライン**（医療情報を取り扱う事業者向け）を
  求められる場面が出る

---

## 1. 認証 — 誰に、何を求めるか

### 結論

| 誰 | 認証 | なぜ |
|---|---|---|
| 患者 | **LINE Login ＋ 店頭での初回ひもづけ** | 患者に手間を作らない。ひもづけが本当の認証 |
| 患者（副系） | メールのワンタイムリンク | LINE 障害時と、LINE を使わない方 |
| セラピスト | メール＋パスワード ＋ 端末ひもづけ | 共有iPadという現場の現実に合わせる |
| 店舗オーナー | メール＋パスワード ＋ **MFA必須** | 全患者のデータに触れられる |
| 自社（super_admin） | **MFA必須 ＋ 申請制・時限アクセス** | 全テナントを見られる。最大のリスクはここ |

### 患者を LINE 認証にしてよいか → **よい。ただし誤解しないこと**

**LINE Login は本人確認ではありません。**
返ってくるのはチャネル内で一意な `userId` だけで、それが証明するのは
「**同じ LINE アカウントが戻ってきた**」ことです。
「この人が田中太郎さんである」ことは証明しません。家族間での端末・アカウント共有は実際にあります。

したがって、**本当の認証は初回のひもづけ**です。
店頭でスタッフが本人を目視確認し、招待トークン経由で
LINE アカウントと患者レコードを1回だけ結ぶ。以後の LINE Login は
「前回と同じ人が来た」の再確認にすぎません。

この形はすでにこのリポジトリの招待フロー（`/invite/[token]`）と同じ構造で、
**設計としては正しい**。変えるべきは実装ではなく、この境界を
自分たちで言語化して、プライバシーポリシーに書くことです。

そのうえで、LINE 固有のリスクは4つ:

1. **アカウント乗っ取り** — 乗っ取られたら要配慮個人情報がそのまま見えます。
   対策: 検査結果の**初回閲覧時だけ**店舗側の再承認を挟む、
   もしくは長期間あいた再ログインで店舗に通知する
2. **単一障害点** — LINE が落ちたら患者は誰もログインできません。
   メールのワンタイムリンクを副系として必ず残す
3. **委託・第三者提供の整理** — LINE Login は認証だけで、検査データは LINE に渡りません。
   この境界を明記する。現在の設計が「LINE で送るのはリンクだけ、数値は送らない」に
   なっているのは正しく、この整理を守るためにも重要
4. **同意の粒度** — 「友だち追加」は「検査結果の表示に同意」ではありません。
   すでに `labtest_view` / `line_share` として分離済み

なお、店舗ごとに公式アカウントがある前提だと、**LINE Login のチャネルも
店舗のプロバイダー側に要ります**。患者IDが店舗ごとに別物になる件とあわせて、
3-2 / 3-4 を参照。

### スタッフを ID＋パスワードだけにしてよいか → **足りません**

パスワード自体が悪いのではなく、**要配慮個人情報を一覧できる画面**に
第2要素が無いのが問題です。最低ライン:

- **オーナーと自社管理者は MFA 必須**（TOTP。Supabase Auth に入っています）
- セラピストは MFA まで求めると現場が回らないので、**端末ひもづけ**で代替。
  登録済みの iPad からのみログインでき、未知の端末はオーナー承認を挟む

そして現場でいちばん起きるのは**アカウントの使い回し**です。
共有iPadに「店舗の共通アカウント」で入ってしまうと、
**監査ログの「誰が」が消えて、監査ログが監査ログでなくなります**。
対策は技術より運用寄り:

- 端末は組織にひもづけ、人はPIN/生体で切り替える（ログインし直させない）
- 同時ログイン数と異常IPを検知して、使い回しを見つける
- 契約書に「アカウントを共有しない」を書く（実効性は低いが、責任の所在は決まる）

## 2. マルチテナントで、いちばん怖いこと

**テナントを跨いだデータ漏れ。1回起きたら事業が終わります。**

現状の土台は良い状態です:

- 全テーブルに `organization_id`
- `current_org_id()` を `auth.uid()` から引く RLS
- ポリシー **99本**、5マイグレーションで `enable row level security`

**穴は RLS の外側にあります。** service-role キーは RLS を迂回するので、
そのキーを使う API ルートは**自分でテナント境界を守らなければなりません**。
書き忘れたら、ID を知っているだけで他店舗のデータに触れます。

service-role を使うルートは現在 10 本。
うち `guide/messages` 系は「書き込みはセッションクライアント、
admin は監査ログのためだけ」という正しい形になっています。

一方、**この監査の途中で自分が入れた `/api/labtest/publish` に、
まさにこの穴が空いていました**（呼び出し元の認証すら無く、
`importId` と `customerId` を知っていれば他店舗の検査を公開できる状態）。
同じコミットの中で塞いでいます — スタッフ本人と組織を確かめ、
更新も `organization_id` で絞る二重の帯にしました。

**再発防止としてやるべきこと**（未着手）:

1. service-role を使うときは、**org スコープを強制するラッパ**を必ず通す
   （生の `getAdminSupabase()` を lint で禁止する）
2. **テナント分離テストを CI に入れる** — 別組織のユーザーで
   全テーブルが読めないことを、テストで固定する。
   RLS は「書いた」だけでは信用できない。破れないことを毎回確かめる

## 3. 店舗ごとの公式LINEに接続する（BYO-LINE）

**店舗はすでに自分の公式アカウントを持っています。** 自社で束ねるのではなく、
店舗のアカウントに接続する形になります。通信費は店舗負担で、
自社の変動費はほぼゼロ。事業としては大きな利点です。

そのかわり、**設計とリスクの重心がここに移ります。**

### 3-1. いちばん重い事実 — 店舗の鍵を預かることになる

店舗のアカウントからメッセージを送るには、その店舗のチャネルの
**シークレットとアクセストークン**を預かる必要があります。

これは検査データとは別種の、そして**血のめぐりの速い**リスクです。
検査データが漏れれば深刻ですが、**チャネルの鍵が漏れれば、
その店舗の全顧客に、店舗の名前でなりすましメッセージを送れます**。
店舗の看板を貸してもらっている以上、ここは検査データと同等以上に守る。

守り方（順に厳しくなる）:

1. **アプリのDB暗号化に頼らない。** 鍵は KMS で別に包む。
   DB のダンプが漏れても、そのままでは使えない状態にしておく
2. **画面にもAPIレスポンスにも返さない。** 一度入れたら二度と読み出せない
   （設定画面には「登録済み ●●●●」とだけ出す）
3. **ログに出さない。** エラー時のリクエストダンプが最頻の漏れ口
4. **長期トークンを持たない。** 短期のアクセストークンを都度発行して使う。
   持ち続けなければ、漏れる面積が小さくなる
5. **失効の導線を用意する。** 店舗が「解約する」と言った瞬間に
   鍵を消せること。消したことを店舗に見せられること

**検討する価値があるのは、そもそも鍵を預からない方法**です。
LINE には SaaS 事業者が店舗の公式アカウントに機能を差し込むための
仕組み（モジュール）があり、これが使えるなら**上の1〜5がまるごと不要**になります。
実装に入る前に、最新の提供条件を必ず確認すること — 設計が変わります。

### 3-2. 患者IDが店舗ごとに別物になる

LINE のユーザーIDは**プロバイダー単位**で一意です。
店舗がそれぞれ自分のプロバイダーで公式アカウントを持っている以上、
**同じ患者でも、店舗が違えば別のIDになります。**

したがって患者の識別子は、単独では意味を持ちません。

```
❌  line_user_id が一意          … 他店舗の同じ人と衝突する / しない が読めない
✅  (organization_id, line_user_id) の組で一意
```

**これはスキーマの決めごとなので、いま決めれば無料、あとから直すと高い。**
現状 `line_user_id` 列はまだ無いので、B4（LINE配信）の実装時に
最初からこの形で入れること。

副次的な効果として、**店舗をまたいだ名寄せが構造的にできません**。
これはテナント分離としてはむしろ望ましい性質です。
「複数店舗で同じ患者を追う」機能は、将来やるとしても
**患者本人の明示的な同意を別に取る**話になります。

### 3-3. Webhook は1本、検証は店舗ごと

店舗ごとにエンドポイントを分ける必要はありません。
LINE の webhook 本文には送信先ボットの識別子が入るので、
**1本の `/api/line/webhook` で受けて、そこからテナントを引く**のが正解です。

ただし順番を間違えないこと:

```
受信 → 本文から送信先を読む → その店舗のチャネルシークレットを引く
     → **そのシークレットで署名を検証** → はじめて本文を信用する
```

署名検証を省くと、誰でも偽のイベントを投げ込めます。
「テナントを引くために本文を先に読む」必要がある以上、
**検証前の本文は一切信用しない**ことを、コードのコメントに残しておくこと。

### 3-4. オンボーディングが、新しい原価になる

通信費が消えたかわりに乗ってくるのがこれです。
店舗ごとに、チャネルの作成・接続・リッチメニューの設置が要ります。

見落としがちな摩擦:

- **店舗にはすでにリッチメニューがある**ことが多い（予約導線など）。
  こちらが上書きすると店舗の既存業務を壊します。
  「1枠だけもらう」のか「差し替える」のかを、契約前に合意する
- **LINE Login チャネルは、公式アカウントと同じプロバイダーに要る**。
  つまり店舗側で作ってもらうか、こちらを管理者に追加してもらう作業が発生する
- **店舗が勝手に設定を変える**。プランを下げる、トークンを再発行する、
  担当者が辞めて誰も触れなくなる → **通知が静かに止まります**
  → テナントごとの疎通チェックと、失敗したら**店舗に**知らせる導線が要る

1店舗あたり**30〜60分の同伴セットアップ**を見込むこと。
10店舗なら誤差ですが、100店舗を目指すならセルフサーブ化が必要になります。
これは「通信費が変動費でなくなったかわりの、新しい変動費」です。

### 3-5. 店舗が患者と直接やりとりできてしまう

店舗の公式アカウントなので、**スタッフは管理画面を通さずに
患者へ個別メッセージを送れます**。これは止められません（店舗の資産なので）。

つまり、**こちらの監査ログの外側でのやりとりが必ず存在します**。
これを事故と捉えるか仕様と捉えるかは決めておくこと。推奨は仕様として受け入れ、
そのうえで**「検査結果そのものは LINE で送らない。送るのはリンクだけ」**という
現在の設計を、契約書と運用ルールの両方に書くことです。
数値を LINE のトーク履歴に置かないかぎり、事故の面積は小さく保てます。

## 4. コスト — 3層に分けて考える

### 層1: 動かすコスト（ほぼ固定になった）

10店舗規模での**目安**。金額は変動するので、契約前に必ず現行価格を確認すること。

| 項目 | 目安（月） | 備考 |
|---|---|---|
| ホスティング（Vercel Pro 相当） | $20 / 席 | |
| DB・認証・ストレージ（Supabase Pro 相当） | $25〜 ＋ compute | **東京リージョン必須** |
| 患者写真のストレージ | 数百円 | 1人月4枚×500KB。1,000人で月2GB。誤差 |
| LINE Messaging API | **¥0（店舗負担）** | 店舗が自分の公式アカウントを持っている前提 |
| AI（ガイド生成） | 数千円 | 1人月1回なら誤差 |
| エラー監視 | $26〜 | |
| バックアップ / PITR | アドオン | 要配慮個人情報なら必須 |

**店舗ごとに公式LINEがあるので、通信費は自社のコストになりません。**
これは事業として大きい — テナントが増えても、変動費がほぼ増えません。
月額固定の SaaS 料金で、粗利が素直に積み上がる形になります。

ただし**タダになったわけではなく、コストの種類が変わっただけ**です。
通信費（変動費）が消えたかわりに、**接続作業（オンボーディング）と、
店舗の鍵を預かるリスク**が乗ってきます。次章。

### 層2: 守るコスト（人件費・固定）

**ここが本命で、月額の半分以上は人件費になります。** 見落としがちな順に:

- 脆弱性対応（例: いま抱えている Next 16 への更新）
- ログの監視と、インシデント発生時の初動
- アクセス権の棚卸し（辞めたスタッフの権限が残る、が最頻の事故）
- 委託先管理（Supabase・Vercel・LINE・Anthropic はすべて委託先。
  要配慮個人情報を扱う以上、選定と監督の記録が要る）
- バックアップからの復旧訓練（やったことがない復旧は、できない復旧）

最低でも **0.2〜0.3人月/月**。これを見ないで価格を決めると必ず赤字になります。

### 層3: 証明するコスト（売り先が大きくなると必須）

| 項目 | 目安 | いつ必要になるか |
|---|---|---|
| サイバー保険 | 年 10〜50万 | **1店舗目の契約前**。いちばん安く買える安心 |
| Pマーク | 取得 30〜60万＋維持、2年更新 | 医療機関と組む段で聞かれる |
| ISMS（ISO 27001） | 初年度 100〜300万 | 法人・チェーン展開の商談で |
| 3省2ガイドライン対応 | 主に人件費と文書化 | クリニック提携を正式化する段 |

**順番が大事です。** 最初から Pマークを取りにいくより、
サイバー保険 → 委託先一覧と安全管理措置の文書化 → 実績ができてから認証、
の順が費用対効果が高い。

## 5. いま決めるべきこと（1店舗目の契約前）

1. ~~LINE公式アカウントを誰が持つか~~ — **店舗が持つ**（確定）。
   通信費は店舗負担、自社は月額固定。かわりに 3章 のリスクを引き受ける
2. **店舗のチャネルの鍵を預かるか、モジュールで預からずに済ませるか** —
   実装前に提供条件を確認する。**設計そのものが変わる**ので、最初に潰す
3. **リッチメニューを1枠もらうか、差し替えるか** — 店舗の既存導線を壊さない。
   契約書のひな形に入れる
4. **オーナーの MFA を必須にするか** — 必須にする。要配慮個人情報なので譲らない
5. **サイバー保険に入るか** — 入る。年10万円台から。
   補償範囲に「店舗アカウントのなりすまし送信」が入るかを確認する
6. **テナント分離テストを CI に入れるか** — 入れる。RLS を「書いた」だけで信じない
7. **副系の認証（メールのワンタイムリンク）を用意するか** — 用意する。
   LINE 単独は単一障害点

## 6. やらないと決めてよいこと

- **患者側のパスワード** — 忘れる、使い回す、問い合わせが増える。
  LINE Login ＋ 店頭ひもづけのほうが安全でも運用でも勝ちます
- **自社での画像の長期保管の作り込み** — Supabase Storage の署名URLで足ります。
  独自実装は事故の面積を増やすだけ
- **最初からの ISMS** — 取れる会社になってからで間に合います
