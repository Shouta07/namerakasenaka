# Vitality Design 事業モデル — 統合レイヤー × プロダクト抽出フライホイール

**版**: v1.0（2026-07）
**位置づけ**: saas-design / topping-architecture の「なぜ勝てるか（構造）」を最上位で言語化したもの。
機能の話（何を作るか）ではなく、**事業の一番強いところ（なぜコピーされないか）**を固定する。

---

## 0. 一言のテーゼ

> **SaaSが増えるほど、Vitality Designの価値は上がる。**
> 院長は「何を選び・どう組み合わせ・どう成果に変えるか」で溺れる。
> Vitality Design は個々のSaaSと戦わず、**その上に立つ「設計者」**になる。
> そして複数の現場で繰り返し必要になった機能だけを、自社プロダクトとして切り出していく。

これは AI 時代に構造的に強い。理由は §3。ただし**無条件では成立しない**。成立条件と罠が §4。

---

## 1. 一番強い構造 — 3層のモート

単機能SaaSは1層で戦う。Vitality Design は3層を積む。上に行くほどコピーされにくい。

```
       ┌─────────────────────────────────────────────┐
  L3   │ 抽出プロダクト（Vitality Designトッピング）           │  ← スケールする収益
       │ 複数院で繰り返し必要になった機能だけを製品化 │     roleplay / copilot / follow-loop …
       ├─────────────────────────────────────────────┤
  L2   │ 統合レイヤー（既存SaaSの"上に乗る"）         │  ← 防御の本体（継ぎ目の所有）
       │ B4A・キレイパス等のデータを吸い、成果に変換  │     data-import + copilot の意思決定ループ
       ├─────────────────────────────────────────────┤
  L1   │ サービス層（現場AX・設計者・月1伴走）        │  ← 信頼の入口（非スケール・ウェッジ）
       │ オペを分解し、型化し、最適な組み合わせを設計 │     山本の talent そのもの
       └─────────────────────────────────────────────┘
```

| 層 | 役割 | スケール | 防御力 | 既存資産 |
|---|---|---|---|---|
| L1 サービス | 信頼を獲得する入口。現場に入りオペを分解 | ✕（人の時間） | 中（属人・関係資産） | mentoring / 現場AX / 導入・体験設計費 |
| L2 統合 | データの継ぎ目を握り、意思決定の場になる | ○ | **高**（乗り換えコスト・多ツール横断） | data-import / copilot |
| L3 プロダクト | 横断で繰り返す機能を製品化し利益を出す | ◎ | 中（機能はいずれ模倣される） | 全トッピング |

**単SaaS（B4A等）はL3だけで戦う。Vitality Designは L1で入り、L2で居座り、L3で稼ぐ。** これが差。

---

## 2. フライホイール — サービスがプロダクトを生み、プロダクトがサービスを軽くする

```
 [1] 現場に入る（L1サービス）
        ↓ オペ分解・課題発見
 [2] その場は手作りで解く（bespoke）
        ↓ 3院で同じ課題が繰り返す
 [3] トッピングとして製品化（L3）        ← 抽出
        ↓ 次の院では"設定"で済む
 [4] 1院あたりのサービス工数が下がる
        ↓ 空いた時間で
 [5] より多くの院に入れる → [1]へ
```

回転が進むほど:
- 1院あたりの**人的コストが下がる**（bespoke → 設定）
- **プロダクト比率（MRR）が上がる**（サービス売上依存から脱却）
- **横断知見が濃くなる**（N院を見ている者しか作れない機能が増える）

---

## 3. なぜ AI 時代に構造的に強いか

1. **SaaS増殖 → 統合の空白が広がる**。ツールは増え続けるが「束ねて成果に変える者」は不在。
   ここは既存ベンダーが埋めない（自社ツールへのロックインが目的なので、競合を含む横断はやらない）。
2. **AIで L3 の製造原価が激減**。昔は「共通機能の製品化」に開発チームが要った。今は現場知見さえあれば
   AI支援で少人数が作れる（本リポジトリのトッピング機構が現に1人+AIで動いている）。
   → **ボトルネックが「作る力」から「現場に入って何を作るべきか見抜く力」に移った**。後者が山本の強み。
3. **山本の talent の productization**。「点で編集して前に出す／現場に入り込む／オペ分解」は、
   まさに L1→L2→L3 のフライホイールそのもの。事業モデルが本人の才能と一致している（＝続く・強い）。

## 4. 成立条件と罠（正直に）

このモデルは魅力的だが、3つの条件を外すと「便利屋コンサル」で終わる。

### 条件A — 統合の"継ぎ目"を必ず所有する（助言で終わらせない）
L2 の防御力は、**Vitality Designが意思決定の起点になっている**時だけ発生する。
「良い組み合わせを提案するアドバイザー」は記憶されず、次年度に切られる。
- 必須: `data-import` で他ツールのデータが**Vitality Designに流れ込む**こと。copilot の提案→実行→効果測定が
  **Vitality Design内で閉じる**こと。これがある限り、他ツールを足しても Vitality Design は外せない。
- 罠: PowerPointの提案書だけ作って実行はクライアント任せ → 継ぎ目を握れず、L2が消える。

### 条件B — 抽出は「3院ルール」（bespoke地獄の回避）
現場で解いた全部を製品化しようとすると、永遠にオーダーメイドで疲弊する。
- ルール: **同じ課題が独立した3院で出たら、初めてトッピング化を検討**する。1〜2院はサービス（手作り）で受ける。
- ルール: 1社目（なめらかせなか）専用実装を Vitality Design 本体に混ぜない（topping-architecture の既存規約）。
- 罠: 目の前の1院に最適化しすぎてコードが分岐 → プロダクトが腐る。

### 条件C — フライホイールが回っている"証拠"を測る
気合ではなく数字で回転を確認する。回っていなければ L1 の便利屋のまま。
- **プロダクト比率** = MRR ÷（MRR + サービス売上）。四半期ごとに上昇しているか。目標: 18ヶ月で 70%超。
- **1院あたりサービス工数**（導入〜安定までの人日）。新しい院ほど減っているか。
- **抽出レイテンシ** = 課題を3院で観測してからトッピング化されるまでの日数。短縮しているか。

## 5. プラットフォームリスクと反論

**Q: B4A・キレイパスが上（L2/enablement）に伸びてきたら?**
- 彼らは**横断できない**。自社データは束ねられても、競合ツールのデータを統合するインセンティブが無い。
  多ツール横断はマルチベンダー中立の第三者（＝Vitality Design）にしか務まらない。
- 彼らは**縦の監修コンテンツを作れない**。医師監修×翻訳辞書×業種特化パックはスケールせず、
  水平プレイヤーが避ける領域（saas-design §2.3b の4資産）。
- それでも一部を模倣される前提で、**L1の関係資産（現場に入った信頼）とL2の継ぎ目**を先に取る。
  機能（L3）は取られてもよい。取られにくい下2層で勝つ設計。

**Q: 逆に Vitality Design がプラットフォーム化して重くならないか?**
- ならない。統合は「取り込み（read）」に徹し、予約・カルテ・会計の**書き戻し（system of record）はやらない**。
  重い責務は既存ベンダーに残す。Vitality Design は軽い enablement 層に留まる。

## 6. 既存資産との対応（今あるものがどこに効くか）

| 既に作ったもの | 効く層 | 役割 |
|---|---|---|
| 月1伴走 / 現場AX / 導入・体験設計費 | L1 | 信頼の入口・ウェッジ |
| data-import（v2） | L2 | 継ぎ目の所有（条件A） |
| copilot の提案→実行→効果ループ | L2 | 意思決定がVitality Design内で閉じる（条件A） |
| トッピング機構（registry / can / 料金表） | L3 | 抽出プロダクトの製造ライン |
| なめらかせなか事例・翻訳辞書・監修コンテンツ | 横串 | 縦ニッチの物語（模倣困難） |

**結論: v2.1 までに作ってきた部品は、この3層モデルにそのまま嵌まる。** 追加で作るべきは機能ではなく、
**フライホイールの計測（条件C）と、data-importで継ぎ目を実際に握ること（条件A）**。

## 7. アーキテクチャは堀ではない — 「蓄積物」の堀（v1.1 追記）

**「データ層→オントロジー→AIエージェント」の3層図は、2026年時点で全プレイヤーの標準スライドになった**
（例: クラシル AIサプライチェーンOS）。業界特化しても、この構造図そのものは誰でも描ける。
クラシル自身の堀も図ではなく最下層の中身 — 4,400万DL の消費者データ・3.5万店舗網・ナショナル
クライアントカバー率93% — である。**堀 = 構造ではなく、運転しながらしか貯まらない蓄積物。**

Vitality Design が持ちうる蓄積物を、獲得可能性つきで正直に列挙する:

| # | 蓄積物の堀 | 中身 | 模倣困難な理由 | Vitality Designの獲得可能性 |
|---|---|---|---|---|
| 1 | **成果ラベル付き会話データ** | 「どの接客の型が成約/継続したか」— roleplay・ai-minutes の会話 × ファネル結果の紐付きコーパス | B4A等は予約・カルテ（結果の記録）は持つが、**会話の中身×成果**は誰も持っていない。Vitality Designのループ内でしか生まれない | ◎ 最重要。設計は今やる（§7.1） |
| 2 | **縦のオントロジー = 翻訳辞書** | 医療語⇔顧客語⇔施術⇔経過の意味ネットワーク。監修つき | 医師監修が要る・スケールしない・業種ごとに作り直し。水平プレイヤーが構造的に避ける | ◎ 既に v0.1 がある（監修医と作成済み） |
| 3 | **横断ベンチマーク** | 「同規模院の平均成約率61%、あなたは48%」— N院を跨ぐ者しか言えない | データのネットワーク効果。1院目からは作れず、先行者に累積する | ○ N=10 から効き始める。规約設計は今（§7.1） |
| 4 | **規制・監修エンジン** | 医療広告GL・薬機法チェックを全AI出力に内蔵 + 監修ネットワーク | 地味・非スケール・責任が重い = 避けられる領域。医療系では信頼の入場券 | ◎ 禁止語フィルタ実装済み。売りに昇格させる |
| 5 | **実行の習慣（ワークフロー所有）** | 気づき→実行→効果がVitality Design内で閉じ、日々の業務動線になる | インサイトはコモディティ。**行動が起きる場所**は乗り換えコストが高い | ◎ copilot ループとして実装済み（条件A） |
| 6 | **チャネルの信頼** | FC本部・経営者コミュニティ・紹介網（クラシルの3.5万店舗網に相当する縦の版） | 関係資産。資金で買えない | ○ なめらかせなかFC・田村さんコミュニティが起点 |
| 7 | **方法論ブランド（教科書化）** | 「成約率の教科書」「接客の型」認定 — 業界の標準語彙になる | 機能は真似できても、業界がその言葉で話し始めたら覆らない | △ 中期。ウェビナー/事例で仕込む |

**持てない堀も明記**: 消費者スケールデータ（クラシル型の4,400万DL）は狙わない。B2B縦特化の
Vitality Design の堀は #1〜#5 の「深さ」であり、広さでは戦わない。

### 7.1 いま設計に入れるべき2点（堀は後付けできない）

1. **成果ラベルのスキーマ**: roleplay_sessions / ai-minutes の記録に、後から
   counseling_records.outcome と結合できるキーを最初から持たせる（#1 の準備。
   データを捨てない設計は初日にしかできない）。
2. **統計利用の同意**: 利用規約に「匿名化・統計化したベンチマーク利用」への同意条項を
   初版から入れる（#3 の準備。後からの規約変更は全テナント再同意になり、実質不可能）。

## 8. 次の一手

1. **条件C の可視化**: 運営ダッシュボードに「プロダクト比率／院あたりサービス工数／抽出レイテンシ」を置く（自分用KPI）。
2. **条件A の最短実装**: data-import の最初の対応を B4A・キレイパスのCSVエクスポートに固定し、
   copilot が外部データ由来の気づき（CPA・再診）を1枚出せる状態にする。
3. **L1の言語化**: 商談の第一声を「設計者」として整える。「ツールが増えて成果が出ないのを、
   束ねて成果に変える役です。既存システムはそのまま、上に乗ります」。
4. **3院ルールの運用開始**: なめらかせなか（1院目）で出た課題を「サービスで受ける／製品化する」に仕分ける台帳を持つ。
