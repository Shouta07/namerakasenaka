# 第1部 サービス設計（ビジネス）

## ミッション

> **美容・ウェルネス店舗の現場CXを創る。**
> 店側の画面（Vitality Design）は「上達と継続」の道具、お客様側の画面は「歩み・お祝い・人の温度・次の一歩」の体験。
> 記録を溜めるためではなく、現場の顧客体験（CX）そのものを商品にするためのプロダクト群である。
> 実装例: `/c/progress` — 進捗の記録を「歩みの物語」（日数・折り返しのお祝い・実感スコアの推移・担当のひとこと・今日のひとつ）として届ける。

## 0. 事業の一番強い構造（最上位テーゼ）

> **SaaSが増えるほど、Vitality Designの価値は上がる。** 院長は「何を選び・どう組み合わせ・どう成果に変えるか」で溺れる。
> Vitality Design は個々のSaaSと戦わず、**その上に立つ設計者**として、L1サービス（現場AX）で入り、
> L2統合（既存SaaSの上に乗る）で居座り、L3プロダクト（横断で繰り返す機能の製品化）で稼ぐ。
> 詳細と成立条件・罠は `docs/vitality-design/moat-and-flywheel.md`。以下 §1〜 はその L3/L2 の具体である。

## 1. プロダクト定義

> **Vitality Design は、クリニック・サロンの「初回カウンセリング」を、いちばん得意な接客に変える SaaS。**
> AI相手の接客練習 × 成約の見える化 × 月1回の伴走で、スタッフの接客を底上げする。
> 記録・写真の経過は本人同意のもと LINE でお客様の手元に届き、成約後の関わりも顧客ごとに蓄積される。
>
> **（v2）そして Vitality Design は、電子カルテ・予約システムと戦わない。それらの上に乗る
> 「クリニック経営のAIレイヤー＝経営コパイロット」である。** 数字を見せるだけでなく、
> 「今週は再診率が低下しています。LINEフォロー対象が42名います」と**次の一手まで提案し、
> その場で実行できる**。個別機能（AI受付・AIカルテ）ではなく、経営の意思決定を支える頭脳が本丸。

### 1.1 解いている課題（誰の・何を）

| 誰 | 課題 | Vitality Design の答え |
|---|---|---|
| オーナー | 成約が「スタッフの感覚」任せで、売上が読めない | ファネルとスタッフ別成約率で数字にする |
| スタッフ | 苦手なお客様（価格比較型・不信型）で失注する。練習相手がいない | AIお客様で何度でも練習、5観点フィードバック |
| 店舗 | 導入したツールが3ヶ月で使われなくなる | 月1伴走で「数字→翌月の練習テーマ」を回し続ける |
| お客様 | カウンセリングの内容を持ち帰れない、経過が見えない | 同意ベースの LINE 経過共有 |

### 1.2 既存資産との関係

- **なめらかせなか（senacare）= 1社目の導入事例**。翻訳辞書・図解・伴走ループ・LINE共有の設計思想は Vitality Design の土台としてそのまま流用する。
- デモは稼働済み（`/vitality-design` 4画面 + モジュール増減機構）。本書はこれを**マルチテナント SaaS に昇格させる**設計である。

## 2. 市場と ICP（理想顧客像）

### 2.1 ターゲット市場（v2.3 で1ニッチに固定）

> **血液検査（血液診断）を接客に使う、肌改善サロン・クリニック**（背中ニキビ・ニキビ跡・肌質改善）。
> **これだけに特化する。** 横展開（脱毛・痩身・審美歯科など）は theme-pack の追加でしか行わない（M13+）。

1ニッチに絞る理由:
- **最重コストの資産が既にこのニッチにある**: 翻訳辞書・腸/栄養の監修レッスン・図解は
  「血液×肌」用に作られており、他業種では作り直しになる
- **検査→翻訳→伴走→再検査 のループが競合空白**: 業務基盤（B4A等）は検査を記録するだけで、
  接客の武器にも再来店エンジンにも変えられない
- **1社目事例と同型の店舗にしか最初は売らない**ことで、コンテンツ制作で溺れず、
  事例の数字がそのまま次の商談に効く

### 2.2 ICP の条件

- 客単価 5万円以上のコース商品がある（成約1件の価値が大きい＝ツール代を1件で回収できる）
- スタッフ 2〜10名（オーナー1人だけだと練習・比較の価値が薄い、大手はSFA領域）
- 初回予約は月 10 件以上ある（集客はできている＝Vitality Design の効果が数字に出る）
- **除外**: 集客に困っている店舗（Vitality Design は集客ツールではない。予約系SaaSと競合しない位置取り）

### 2.3 競合と差別化

| 分類 | 例 | 彼らの主戦場 | Vitality Design の違い |
|---|---|---|---|
| クリニック業務基盤（オールインワン） | **B4A**（予約・電カル・決済・CRM・経営ダッシュボード・在庫・シフト。500院〜） | 業務の記録と効率化（system of record） | **戦わない・上に乗る**。彼らが持つデータを data-import で受け、「人の上達と関係の質」に変換する |
| 同上・低価格 | **キレイパスコネクト byGMO**（電カル+予約+経営分析+CRM、月¥9,000〜） | 同上 | 同上。価格でも機能数でも競わない |
| 予約・POS（サロン系） | リザービア 等（月1.5〜3.3万円） | 予約獲得・決済 | 併用される前提 |
| 接客研修 | 研修会社・コンサル（1回数十万） | 単発研修 | 毎日練習できる。数字と接続。1/10 の価格で常設 |

### 2.3b 正面衝突の回避（v2.1 重要）

**「経営分析・経営ダッシュボード」を看板にしない。** B4A・キレイパスは予約/カルテ/会計の
一次データを持つ側であり、その土俵の分析勝負は構造的に不利（燃料も価格も負ける）。

Vitality Design のカテゴリは彼らと別物として立てる:

> **彼ら = 記録のシステム（system of record）。Vitality Design = 上達のシステム（system of enablement）。**
> 業務を記録・効率化するツールは揃った。しかし「**人の接客が上手くなる**」「**患者との関係の質が上がる**」
> ツールは存在しない。Vitality Design はそこにだけ立つ。

- コパイロットのスコープは **成約・継続・練習（人のパフォーマンスループ）に限定**。
  在庫・会計・シフト・売上全般の分析は**やらない**と明言する（§8B スコープ参照）
- B4A・キレイパス導入院は競合ではなく**見込みリスト**。「お使いの system はそのままで、
  上に Vitality Design を乗せる」が営業の第一声。data-import の最初の対応フォーマットは両社のCSVエクスポート

**山本にしかできないこと（機能ではなく方法論・関係資産＝コピーされにくい）**:
1. **翻訳者ポジション** — 監修医（医療知見）× 現場 × 顧客語の翻訳パイプライン。翻訳辞書・
   医師監修の図解/レッスンは、SaaS企業が構造的に持てない（監修ネットワークとコンテンツ制作はスケールしないため避ける領域）
2. **現場AX の入り込み** — オペを分解し型化して月1伴走で回す。500院を抱える業務基盤ベンダーには
   この価格帯でハイタッチは打てない
3. **縦ニッチの物語** — なめらかせなか（背中ケア）の1社目実装と成果数字。コンプレックス系
   （感情に寄り添う体験設計）という思想ごと縦に深い
4. **業界特化コンテンツ** — テーマパック（腸・食事・スキンケア・運動→肌再生・ニキビ跡…）で
   縦ニッチを1つずつ制圧する。横に広い B4A はニッチごとの監修コンテンツを作れない

**一言の差別化（v2.1）**: 「記録するツールは、もうお持ちのはず。**Vitality Design はスタッフを上手くし、
患者さんとの関係を深くする方のツール**です。お使いのシステムの上にそのまま乗ります」

### 2.4 ペイン → 価値マップ（v2・設計の背骨）

自由診療・美容クリニックのペインを6領域に棚卸しし、Vitality Design の提供価値と既存資産に対応付ける。
新機能の追加判断は必ずこの表に載るかで行う。

| # | ペイン領域 | 代表ペイン | Vitality Design の価値 | 対応トッピング |
|---|---|---|---|---|
| 1 | 集客・経営 | CAC高騰 / リピート率低 / LTV伸びない / キャンセル多 | リピート率・LTV向上、自動フォロー、患者分析 | follow-loop / at-risk（既存）+ copilot |
| 2 | カウンセリング | 成約率が人で違う / ノウハウ属人化 / 新人教育が重い | AI議事録、AIフィードバック、成約率分析、ベスプラ共有 | roleplay / dashboard（既存）+ **ai-minutes（新）** |
| 3 | スタッフ | 採用難 / 離職 / 教育コスト / 院長が現場に張り付く | 教育コンテンツ、AIマニュアル、KPIダッシュボード | lessons / roleplay（既存）+ **staff-kpi（新）** |
| 4 | オペレーション | LINE対応 / 電話 / 写真管理 / 二重入力 | 自動連携、ワークフロー削減 | line-share / photos（既存）+ **data-import（新）** |
| 5 | 医療品質 | 経過観察が属人的 / 再診タイミング最適化されず | AI経過観察、リスク検知、自動リマインド | evidence / at-risk / follow-loop（既存） |
| 6 | **経営管理** | **数字が見えない / 利益率不明 / 次の施策が打てない** | **経営ダッシュボード + AI経営分析 + アクション提案** | **copilot（新コア・§8B）** |

**院長が本当に困っているのは⑥**。①〜⑤の機能群が生むデータを、⑥のコパイロットが「気づきと次の一手」に変換する——これが v2 の全体構造。

### 3.2 価格の根拠

- Standard ¥29,800 = **コース1件の成約増（客単価10万円前後）の 1/3 以下**。「月に1件、練習の成果で成約が増えれば3倍返し」という営業ロジック
- 予約系SaaS（1.5〜9万円）と同レンジに収め、稟議の相場観を外さない
- 月1伴走の人件費は Pro/Standard の粗利内に収まる（§3.4）

### 3.3 MRR ¥1,000,000 の構成モデル

**基本式**: MRR = 店舗数 × ARPU

| シナリオ | 構成 | MRR |
|---|---|---|
| **A（本命）** | Standard×25 + Pro×5 = **30店舗** | ¥994,000 |
| B（分散） | Starter×10 + Standard×15 + Pro×8 = 33店舗 | ¥993,400 |
| C（クリニック寄せ） | Standard×10 + Pro×14 = 24店舗 | ¥995,200 |

→ **目標は「有償30店舗・ブレンドARPU ¥33,000」**。テーマパック・初期費は上乗せ（MRRに数えない）。

## 4. GTM（拡販戦略）

### 4.1 販売チャネル（優先順）

1. **導入事例エンジン（なめらかせなか）** — 「成約率 53%→61%」のような数字つき事例を最初の3ヶ月で作る。事例がない SaaS は売れない。**田村さんの経営者コミュニティへの紹介**が最初の5社の主経路
2. **紹介プログラム** — 紹介1件成約で紹介者に ¥30,000 or 利用料1ヶ月無料。ICP同士は横で繋がっている業界
3. **FC・多店舗本部営業** — なめらかせなかが FC 再展開すれば1契約×n店舗。本部向け Pro 一括が最短の MRR ジャンプ
4. **コンテンツ/セミナー** — 「成約率の教科書」ウェビナー月1回。デモ（/vitality-design）をその場で触らせる
5. **パートナー** — 予約系SaaS・ディーラー・補助金支援会社（ライトアップ社）との相互送客。IT導入補助金の**ベンダー登録は M13 以降**に検討（販売が回証明されてから）

### 4.2 セールスファネル目標（巡航時・月次）

```
リード 20 → 商談 10 → トライアル 6 → 有償化 4 （商談→有償 40%）
解約 ▲0.5店/月 → 純増 +3.5店/月
```

### 4.3 MRR 成長ロードマップ

| 期 | 店舗数(累計) | MRR | 焦点 |
|---|---|---|---|
| M1〜3 | 1（なめらかせなか） | ¥30,000 | 事例づくり。数字を採る。SaaS基盤開発 |
| M4〜6 | 5 | ¥120,000 | デザインパートナー5社（特別価格 ¥19,800、フィードバック契約） |
| M7〜9 | 10 | ¥300,000 | 正価販売開始。紹介プログラム稼働 |
| M10〜12 | 18 | ¥550,000 | 伴走の型化。クリニック業種パック投入 |
| M13〜15 | 25 | ¥800,000 | FC/多店舗案件 1〜2件。パートナー送客 |
| **M16〜18** | **30〜33** | **¥1,000,000** | 達成。以後は Pro 比率と expansion で ARPU 向上 |

### 4.4 撤退・転換ライン（先に決めておく）

- M6 時点で有償3社未満 → 価格 or ICP を再設計（機能を作り足さない）
- M12 時点で MRR ¥40万未満 or 月次解約 >4% → 高タッチ・高単価の「SaaS付きコンサル」（月10万×10社）へピボット

## 5. KPI ツリー

```
MRR ¥100万
├─ 新規獲得: リード数 / 商談化率 / トライアル開始率 / 有償化率(≥60%)
├─ 継続: 月次解約率(≤2%) ← 先行指標: 週次ログイン店舗率(≥80%) / 月間練習セッション数/店(≥20) / 伴走実施率(100%)
└─ 単価: プランmix / テーマパック added / 年払い比率(≥40%)
```

**North Star Metric**: 「週に1回以上、練習 or ダッシュボード閲覧をした店舗の割合」— これが 80% を切ったら解約が3ヶ月後に来る。

```
       └─ Edge Functions（署名検証・非同期ジョブ）
```

**方針**

- 現行デモ（senacare リポジトリ）の設計思想を継承しつつ、**Vitality Design は独立リポジトリ・独立 Supabase プロジェクト**に切り出す（テナントデータと1社目カスタム実装を混ぜない）
- デモモード機構（env 未設定時 localStorage）は営業デモ用に**維持**する — `/vitality-design` デモがそのまま営業資産になる
- モノリス（Next.js + Supabase）で M12 まで引っ張る。マイクロサービス化はしない

## 8. AIロールプレイ設計（コア差別化機能）

### 8.1 構成

```
Client (chat UI, streaming表示)
  → POST /api/roleplay/[sessionId]/turn   … スタッフ発話を送る
  → Next.js Route Handler:
      1. entitlement チェック（残セッション数）
      2. Claude API 呼び出し（streaming, persona system prompt はキャッシュ）
      3. turn を DB 保存、SSE でクライアントへ
  → 練習終了時 POST /api/roleplay/[sessionId]/feedback
      … 全会話を渡して採点（structured outputs で rubric JSON を強制）
```

### 8.2 モデルと呼び出し方針

| 用途 | モデル | 理由 |
|---|---|---|
| お客様役の会話 | `claude-opus-4-8`（標準） | ペルソナの一貫性・自然な感情表現が商品価値そのもの |
| 採点フィードバック | `claude-opus-4-8` + structured outputs | rubric JSON を `output_config.format`(json_schema) で保証 |
| 伴走レポート下書き | `claude-opus-4-8` | 月1回・低頻度なので品質優先 |
| コスト最適化オプション | `claude-sonnet-5` へ切替可能な設計 | model はテナント設定ではなく**サーバ側 config** で一元管理 |

実装上の要点:

- **プロンプトキャッシュ必須**: system（ペルソナ定義 + 採点rubric + 禁止語ルール ≒ 3〜4K tokens）に `cache_control` を置く。会話が進むほど読み取りはキャッシュヒット
- **streaming 必須**（体感応答 < 2秒）。`client.messages.stream()` + `finalMessage()`
- 採点は `output_config: {format: {type: "json_schema", …}}` で `{score, passed[], advice[]}` を強制。パース失敗リトライを排除
- **禁止語フィルタ（senacare §8.2 継承）**: 生成後にサーバ側で医療広告・薬機法 NG 表現を後置チェック。ヒット時は再生成
- ペルソナは `persona_json`（性格・背景・失注理由・感情遷移ルール）として DB 管理。**台本エンジン（現行デモ）は fallback** として残し、API 障害時も練習を止めない

### 8.3 フェアユースとガードレール

- プラン別セッション上限（entitlements）。超過時は「今月の練習枠を使い切りました」→ アップセル導線
- 1セッション最大 20 ターン・30分。1テナント同時 3 セッションまで
- 月次トークン集計を `roleplay_sessions.token_usage_json` に保存 → 原価ダッシュボード（運営用）

### 8.4 AI 原価計算（プライシングの裏付け）

前提: 1セッション = 会話10往復 + 採点1回。system 3.5K tokens はキャッシュ、履歴は逐次成長（平均 input 2.5K/回、output 350/回）。

| モデル | 1セッション原価 | 100セッション/月 |
|---|---|---|
| Opus 4.8（$5/$25 per MTok） | ≈ $0.21〜0.28（**¥35〜45**） | **¥3,500〜4,500** |
| Sonnet 5（$3/$15、〜2026-08 は $2/$10） | ≈ $0.08〜0.13（¥13〜20） | ¥1,300〜2,000 |

→ Standard（¥29,800・100回）で AI 原価率 **7〜15%**。粗利目標 80% の範囲内。無制限の Pro はフェアユース（実績上限 300回/月）で上振れを抑える。

## 8B. コパイロット設計（v2 新設・コア差別化の第2弾）

> **スコープ（v2.1）**: コパイロットの気づき・提案は **成約・継続・練習（人のパフォーマンスループ）に限定**する。
> 在庫・会計・シフト・売上全般の「経営分析」は B4A・キレイパス等の業務基盤の領域であり、扱わない（§2.3b）。
> 対外的な呼称も「経営コパイロット」ではなく「**接客と継続のコパイロット**」とする。

### 8B.1 北極星の体験

> 「今週は再診率が低下しています。LINEフォロー対象が42名います。→ **[一括フォローを準備する]**」
> 「田村さんは成約率が平均より12%高く、ヒアリング時間は短い傾向です。→ **[この型を練習シナリオ化する]**」

見せるだけのBIと違い、**気づき → 打ち手の提案 → Vitality Design内でワンタップ実行 → 効果測定**が
1つのループとして閉じる。実行ボタンの先は既存トッピング（LINE一括フォロー＝line-share、
シナリオ化＝roleplay）なので、コパイロットは全機能の**利用を促す司令塔**にもなる。

### 8B.2 インサイトエンジン（3層）

```
第1層 ルール（純関数）   … lib/retention・lib/evidence と同じ思想。日次スナップショットから
                          「事実」を検出（再診率低下・成約率の偏り・キャンセル集中 等）。
                          テスト可能・説明可能・ハルシネーションなし
第2層 LLM（Claude）      … 検出された事実の束を自然文ブリーフ + 打ち手提案に合成。
                          structured outputs で {insight, evidence[], proposed_action} を強制。
                          禁止語フィルタ・因果を断定しない表現規則（evidence §8 コピー規則）を通す
第3層 アクション         … 提案に実行ボタンを紐付け（LINE一括フォロー / 練習テーマ割当 /
                          リマインド設定変更）。実行・却下・結果を copilot_insights に記録
```

原価: ブリーフ生成は 1日1回/テナント（Standard は週1回）。1回 ≈ 入力5K + 出力1K tokens →
Opus 4.8 で ≈ ¥8/回。日次でも **月 ¥250/店** と、ロールプレイより1桁小さい。

### 8B.3 データ設計（§7.3 への追加テーブル）

```sql
-- 日次メトリクス（コパイロットの燃料。Vitality Design内データ + data-import の外部データを集約）
metrics_daily(
  organization_id, date,
  bookings, visits, counselings, proposals, contracts,   -- ファネル
  revisits, cancellations, no_shows,
  line_follows_sent, practice_sessions,
  revenue_jpy NULLABLE, ad_cost_jpy NULLABLE,             -- data-import 由来
  per_staff jsonb                                          -- スタッフ別内訳
)

-- 気づきと提案（提案→実行→効果が1レコードで追える）
copilot_insights(
  id, organization_id, created_on,
  severity,                    -- 'attention' | 'opportunity' | 'info'
  insight_text, evidence jsonb,             -- 第1層が検出した事実（数値つき）
  proposed_action jsonb,                    -- {kind, label, target_topping, params}
  status,                      -- 'open' | 'done' | 'dismissed'
  acted_at, acted_by,
  outcome jsonb                 -- 効果測定（例: フォロー42名中9名が再来店予約）
)
```

### 8B.4 ガードレール

- スタッフ別の数字は**「責めるためではなく、練習テーマを決める材料」**をUI文言として常設（staff-kpi と共通の文化制約）
- 因果を断定しない（「〜が効いた可能性があります」）。医療広告・薬機法の禁止語フィルタを全ブリーフに適用
- 外部データ（data-import）が無くても Vitality Design 内データだけで動く。連携は精度を上げる追加燃料という位置づけ
- 提案の実行は必ず人の承認を挟む（自動送信はしない）。実行ログは監査ログに記録

## 9. モジュール & エンタイトルメント設計

「機能を増減できる」を課金と直結させる。**モジュール定義（現行 `VITALITY_DESIGN_MODULES`）を DB 化**し、プラン → エンタイトルメントに写像する。

```
plans (starter/standard/pro)
  └─ plan_modules(plan, module_id, limit_value)      … プランの既定
organizations
  └─ entitlements(org, module_id, enabled, limit_value, source)
       source: 'plan' | 'addon' | 'trial' | 'manual'
```

- UI のトグル（現行実装）はそのまま「**使う/使わない**」。課金上のオン/オフは entitlement が上位
- テーマパック購入 = `entitlements(source='addon')` + コンテンツ行の解放
- 判定はサーバ側 `can(org, module, usage)` 一箇所に集約。クライアントは表示制御のみ

## 10. 課金設計（Stripe）

- **Stripe Billing / subscription**。Product: `vitality_design_starter/standard/pro`（月次・年次 Price）、`theme_pack`（one-time）、`setup_fee`（one-time）
- フロー: 14日トライアル（クレカ必須）→ 自動課金開始。Webhook（`checkout.session.completed`, `customer.subscription.updated/deleted`, `invoice.payment_failed`）→ `entitlements` 同期
- 支払い失敗: Smart Retries + 7日猶予（バナー表示）→ 14日で read-only 化（**データは消さない**。解約後90日保持）
- Pro の請求書払いは Stripe Invoicing（銀行振込）
- 税: 税抜表示 + Stripe Tax で消費税自動計算
- 解約はセルフサービス（画面から）+ 解約理由アンケート必須

## 11. LINE 連携設計

- **店舗ごとに LINE公式アカウントを店舗名義で開設**（Messaging API チャネル）。Vitality Design に channel secret / access token を登録（暗号化保存）。※Vitality Design 名義の単一チャネルにしない — 顧客から見た差出人は店舗であるべき + 従量課金を店舗負担にできる
- 友だち追加: 店頭 QR（Vitality Design が生成）→ `line_user_id` と `customers` を紐付け（初回カウンセリング時にスタッフが照合）
- **同意ファースト（現行デモの設計を昇格）**:
  - `line_consents` に取得日時・スコープ（経過写真/要約/予約案内）・取得方法を記録
  - 同意がない顧客には**送信 API 自体が 403**（UI 制御ではなくサーバ強制）
  - 顧客はいつでも LINE から「配信停止」→ consent revoke → 以後送信不可
- 送信物: 経過ページへのリンク（`/share/[token]`、有効期限つき・失効可能トークン）。**写真そのものを LINE に直接送らない**（誤送信・転送リスクの低減）
- Webhook 受信（友だち追加/ブロック/メッセージ）は Edge Function で署名検証 → キュー処理

## 12. セキュリティ・コンプライアンス

健康状態・肌状態・施術写真は**要配慮個人情報に準じて扱う**。ここが競合に対する信頼の壁になる。

| 領域 | 設計 |
|---|---|
| テナント分離 | Postgres RLS（§7）+ Storage も org プレフィックス + 署名URL（短寿命） |
| 認証 | Supabase Auth（メール + パスワード + 招待制）。owner は 2FA 推奨 |
| 暗号化 | 転送 TLS / 保存時暗号化（Supabase 既定）+ LINE トークン等はアプリ層でも暗号化 |
| 監査 | `audit_logs` に閲覧・出力・共有・運営 impersonate を記録（1年保持） |
| データ削除 | 顧客単位の削除 API（お客様からの要請対応）/ 解約後90日で全削除。写真は物理削除 |
| バックアップ | Supabase PITR（Pro）+ 日次スナップショット。復旧目標 RPO 24h / RTO 12h |
| AI への入力 | ロールプレイに実顧客の個人情報を入れない設計（ペルソナは架空 + 統計化した失注理由のみ）。プロンプトに PII を渡す機能は M12 まで作らない |
| 表現コンプラ | 禁止語フィルタ（医療広告ガイドライン・薬機法 NG 語）を全 AI 出力と店舗発信テンプレに適用 |
| 規約類 | 利用規約 / プライバシーポリシー / 特商法表記 / セキュリティチェックシート雛形（クリニック商談で必ず要求される）|
